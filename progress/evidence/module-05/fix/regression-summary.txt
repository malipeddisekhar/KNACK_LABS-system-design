Topic: Swallowed Database Exception during Write

1. ROOT CAUSE EXPLANATION
--------------------------------------------------------------------------------
In `api/src/links/links.service.ts`, inside the `create()` method:
A `try/catch` block wraps the database insertion `await this.prisma.link.create(...)`.
During BREAK, an improper fallback was introduced into the `catch (error)` block:
instead of re-throwing unexpected database errors with `throw error;`, the catch
block swallowed the exception and returned a fabricated link object:
`{ id: '00000000-0000-0000-0000-000000000000', code, ... }`.

Because NestJS methods returning values resolve with HTTP 201 Created by default,
this silent suppression caused:
1. False-Positive Success: The client received HTTP 201 Created and assumed the
   link was stored durably.
2. Silent Data Loss: No record was ever written to PostgreSQL.
3. Downstream 404s: Calling `GET /links/:id` with the returned dummy ID immediately
   returned HTTP 404 Not Found.
4. Broken Observability: Because the exception was swallowed in the service layer,
   it never reached `HttpExceptionFilter`, so no structured 500 error log was emitted.

2. CODE CORRECTION IMPLEMENTED
--------------------------------------------------------------------------------
File: `api/src/links/links.service.ts`

Lines 85-97:

Key Fix Properties:
1. Removed the fake fallback object completely.
2. Preserved the duplicate-code retry loop for Prisma error `P2002` (up to 3 attempts).
3. Preserved `ServiceUnavailableException` (HTTP 503) when retry attempts are exhausted.
4. Restored `throw error;` for any unexpected database failures.
5. The propagated error bubbles up to `HttpExceptionFilter`, which:
   - Maps unexpected errors to `HttpStatus.INTERNAL_SERVER_ERROR` (500).
   - Generates a safe error envelope `{ error: { code: 'INTERNAL_SERVER_ERROR', message: '...', request_id: '...' } }`.
   - Populates `request_id` matching the `X-Request-ID` response header.
   - Logs structured JSON with latency, route, status code, and request ID.
   - Redacts internal stack traces and database credentials from the client response.
